# Loaded-carry shuttle

Place `core/loaded-carry@1` on clear supported ground and put one `core/carry-weight@1` on an ordinary work table.
A Soul normally picks up the actual weight, discovers the course and sends `object:<course-id>:carry-shuttle`.
The kind declares the act and its persisted state; no new word rule or client behavior is required.

The native plan walks to the start stripe, to the stripe four authored metres away, then back and stands. Route
coordinates follow the course's world rotation and scale. Navigation owns all movement and may detour or refuse.
Active sessions sample the real item's native in-hand support and same body each native observation tick. A sampled
drop, changed load/body, permission, course or floor invalidates credit. Only a matching completed receipt with both
observed route milestones changes the course's record. This is not a sub-tick custody guarantee, actual travel-distance
measurement, fitness/strength model or automatic pickup. The authored mass comes from the same weight definition.

Current course inspection gives its requirements, completed count and historical participant/load/nominal route span.
No current foreign-object oracle or idle world scan is introduced. Other native item handling remains authoritative.
Completed records use the shared engine-authored completion adapter and survive unrelated God Undo/redo.

Named `loadedCarry` hooks in actuators, perception and the bridge, plus its active-session tick call, are independent
additions. Claude must integrate these serially with other action branches. Exact structural/catalog/completion
candidate dependencies remain separately qualified and require steward integration; no full-client or deployment claim.
